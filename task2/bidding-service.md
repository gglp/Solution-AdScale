# Спецификация Сервиса ставок (Bidding Service)

## Назначение и границы

Сервис ставок — результат объединения функций приёма запроса и логики аукциона в единый сервис. Он отвечает за приём bid-запроса от DSP-партнёра, отбор кандидатов среди активных кампаний AdScale, взвешивание ставок по бизнес-правилам и определение победителя — с P95 времени отклика ≤ 80 мс.

**Что входит в границы сервиса:**
- Приём и валидация bid-запроса (структура OpenRTB, обязательные поля).
- Определение пользователя/контекста показа (таргетинг: гео, устройство, площадка).
- Отбор кандидатов — кампаний, соответствующих таргетингу и имеющих остаток бюджета.
- Взвешивание ставок и выбор победителя аукциона.
- Формирование bid-ответа (совместно с Сервисом выдачи, который рендерит разметку баннера).

**Что НЕ входит в границы сервиса (явно вынесено в другие сервисы):**
- Списание бюджета по факту показа/клика — в Финансовом сервисе, на основе событий из Очереди событий.
- Хранение и агрегация статистики показов/кликов — в Сервисе статистики и Сервисе аналитики.
- Управление кампаниями (создание, редактирование, приостановка, хранение источника истины по бюджету и таргетингу) — в Сервисе кампаний; Рекламный кабинет обращается к Сервису кампаний напрямую как к отдельному сервису. Сервис ставок потребляет эти данные только через контракт, описанный ниже.
- Формирование HTML/JS-разметки баннера — в Сервисе выдачи.

## Внешний API (для DSP-партнёра, через API Gateway)

Контракт — протокол **OpenRTB поверх HTTPS**, формат сохраняется без изменений. Один эндпоинт:

```
POST /rtb/bid
Content-Type: application/json (OpenRTB BidRequest)

→ 200 OK, тело — OpenRTB BidResponse (bid + adm с разметкой баннера)
→ 204 No Content — AdScale не участвует в аукционе (нет подходящей кампании / бюджет исчерпан)
→ 5xx — обрабатывается Circuit Breaker на API Gateway (см. api-gateway.md)
```

Требование по времени: DSP-партнёр ожидает ответ в пределах своего auction timeout (обычно 100–120 мс на стороне DSP); бюджет AdScale на обработку — P95 ≤ 80 мс, что оставляет DSP-партнёру запас на сетевую задержку.

## Внутренний API (для вызовов из других сервисов AdScale)

Формат и обоснование выбора gRPC — см. [`interaction.md`](./interaction.md). Сервис ставок экспонирует только один метод, соответствующий его единственной внешней ответственности — принять решение по ставке:

```protobuf
service BiddingService {
  // Синхронный вызов из API Gateway
  rpc EvaluateBid(BidContext) returns (BidDecision);
}

message BidContext {
  string impression_id = 1;
  Geo geo = 2;
  Device device = 3;
  repeated string placement_categories = 4;
}

message BidDecision {
  bool has_bid = 1;
  string campaign_id = 2;
  double price_cpm = 3;
  string creative_ref = 4;
}
```

## Контракт Bidding ↔ Campaign

Сервис ставок — клиент Сервиса кампаний. Контракт состоит из двух независимых каналов с разными протоколами, выбранными под разный профиль использования:

**1. Синхронный bulk-запрос — только для прогрева, не в hot path.**

```protobuf
service CampaignService {
  // Вызывается Сервисом ставок только при старте инстанса
  // (или по явной команде принудительного прогрева).
  // НЕ участвует в обработке bid-запроса.
  rpc GetActiveCampaigns(GetActiveCampaignsRequest) returns (CampaignSnapshot);
}
```

*Протокол: gRPC.* Хотя этот вызов не в hot path и по чистой задержке мог бы обойтись REST, gRPC выбран ради единообразия внутреннего контракта между сервисами (весь внутренний трафик AdScale — gRPC, REST зарезервирован за браузерным клиентом Рекламного кабинета — правило зафиксировано в `interaction.md`) и ради компактной бинарной сериализации: при прогреве передаётся полный снимок активных кампаний, который может быть объёмным.

**2. Асинхронные события — основной канал поддержания актуальности кеша.**

Сервис кампаний публикует `campaign.updated`, `campaign.budget.updated`, `campaign.activated` в Kafka при любом изменении; Сервис ставок потребляет их отдельным внутренним компонентом (cache-updater) и обновляет Кеш. Это, а не bulk-запрос, — основной путь, которым Сервис ставок узнаёт об изменениях: bulk-запрос закрывает только холодный старт. Подробности потоков и схема событий — в [`interaction.md`](./interaction.md).

Оба канала независимы: отказ одного не блокирует другой (авария Kafka не мешает прогреву по bulk-запросу при рестарте; недоступность Сервиса кампаний на момент старта не мешает работать по уже накопленным в Кеше данным).

## Зависимости

| Зависимость | Тип вызова | Роль | Поведение при отказе |
|---|---|---|---|
| Кеш (Redis) | Синхронный, in-memory, hot path | Источник горячих данных по кампаниям и ставкам | Circuit Breaker → fallback на локальный snapshot / дефолтную ставку (см. «Надёжность») |
| Сервис кампаний — bulk-запрос (gRPC) | Синхронный, НЕ в hot path, только при старте инстанса | Прогрев Кеша полным снимком активных кампаний | Инстанс не переходит в `ready`, пока прогрев не завершится (retry с backoff — см. «Надёжность»); уже запущенные инстансы не затронуты |
| Сервис кампаний — события (Kafka) | Асинхронный, НЕ в hot path | Основной канал обновления Кеша при изменении кампаний/бюджетов | Кеш продолжает работать на последних применённых событиях; отставание потребителя устраняется репроигрыванием (replay) из Kafka |
| Сервис выдачи | Синхронный, внутренний вызов | Формирование разметки баннера для победившей кампании | Circuit Breaker → бид без разметки (nurl-подход: разметка баннера не передаётся сразу внутри bid-ответа — «inline» — а отдаётся по отдельному запросу площадки в момент фактического показа, по notification URL) |
| Очередь событий (Kafka) | Асинхронный, fire-and-forget из Сервиса выдачи | Публикация события показа для статистики/биллинга | Не блокирует критичный путь; при недоступности Kafka событие ретраится вне hot path |

## Модель данных

**Модель Сервиса кампаний (для контекста; не является БД Сервиса ставок — приведена, чтобы показать, какие данные попадают в Кеш через контракт выше):**

| Таблица | Ключевые поля | Назначение |
|---|---|---|
| `campaigns` | `id`, `advertiser_id`, `status`, `budget_total`, `budget_spent`, `max_cpm`, `start_at`, `end_at` | Кампания рекламодателя и её бюджетные ограничения |
| `targeting_rules` | `campaign_id`, `geo_codes[]`, `device_types[]`, `placement_categories[]` | Условия таргетинга для отбора кандидатов |
| `creatives` | `id`, `campaign_id`, `creative_ref` | Ссылка на разметку баннера для Сервиса выдачи |

**Кеш (Redis) — собственная read-модель Сервиса ставок, денормализованная под hot path:**

- `campaign:{id}` → сериализованный объект кампании (бюджет, ставка, статус); наполняется и обновляется через контракт с Сервисом кампаний (bulk-запрос при старте + события при изменениях), не напрямую из БД Сервиса кампаний.
- `targeting_index:{geo}:{device}` → множество (Redis Set) `campaign_id`, соответствующих условию — позволяет отбирать кандидатов без полного перебора и без обращения к Сервису кампаний на каждый bid-запрос.
- `budget_remaining:{campaign_id}` → счётчик с атомарным декрементом (Redis `DECRBY`) для быстрой проверки остатка бюджета в hot path; финальная сверка со списаниями Финансового сервиса происходит асинхронно и может корректировать значение.

## Надёжность

Circuit Breaker, retry и fallback ниже защищают Сервис ставок от отказа **конкретной зависимости** в момент обращения к ней. Это не то же самое, что отказоустойчивость **самого компонента** (сколько у него инстансов, как они распределены, что происходит при потере одного из них) — та описана отдельно, в разделе «Стратегия отказоустойчивости» ниже.

**Circuit Breaker (вызовы к зависимостям):**
- К Кешу: порог открытия — 50% ошибок/таймаутов за скользящее окно 10 секунд или 20 последовательных ошибок. При открытом состоянии — сразу fallback, без попытки вызова.
- К Сервису выдачи: аналогичный порог; при открытом состоянии — bid-ответ формируется без inline-разметки (nurl-подход, см. «Зависимости» выше).
- Half-open: одна пробная попытка каждые 5 секунд; при успехе — закрытие цепи.

**Повторные попытки (retry) с экспоненциальной задержкой:**
- Применяются только к вызовам вне критичного по SLA пути — bulk-запрос к Сервису кампаний при старте инстанса: 3 попытки, база 100 мс, множитель ×2, джиттер ±20%.
- В синхронном hot path (Шлюз → Сервис ставок → Кеш) retry не используется — при бюджете 80 мс на весь запрос повторная попытка может вызвать превышение SLA; вместо retry — быстрый fallback.

**Резервные стратегии (fallback):**
- При недоступности Кеша (Circuit Breaker открыт) используется отдельный **локальный snapshot** — процесс-локальный (in-memory) снимок последних валидных данных по кампаниям и ставкам, который фоново пополняется из Кеша, пока тот доступен, и живёт в самом инстансе Сервиса ставок независимо от Redis (компонент `Fallback Snapshot`, см. component-диаграмму). Если данных по конкретной кампании нет даже в снимке — используется дефолтная консервативная ставка для площадки.
- При недоступности Сервиса выдачи — ответ DSP-партнёру без inline creative (см. выше), показ обрабатывается позже по notification URL.

## Стратегия отказоустойчивости (Failover Strategy)

Раздел описывает, как каждый компонент остаётся доступным при отказе одного из своих узлов/инстансов — вопрос, отдельный от Circuit Breaker/retry/fallback выше.

**Сервис ставок: Active-Active.**
Сервис полностью stateless — всё состояние вынесено в Кеш и локальный snapshot, сам процесс не хранит ничего, что нельзя было бы восстановить прогревом. Поэтому все инстансы во всех зонах доступности одновременно активны и принимают трафик через балансировку на Шлюзе; отказ одного инстанса — это просто исключение его из пула балансировки, без выборов лидера и без периода недоступности. Active-Passive здесь означал бы резерв мощности, не участвующий в обслуживании трафика, что противоречит требованию горизонтального масштабирования до 50 000 RPS — простаивающая пассивная копия не помогает нести эту нагрузку.

**Сервис кампаний / бюджет: Active-Passive (Master-Slave) с автоматическим failover.**
В отличие от Сервиса ставок, здесь единственный источник истины для записи — реляционная БД, и активно-активная запись в двух местах потребовала бы разрешения конфликтов при одновременном редактировании бюджета одной кампании, что неприемлемо для данных такого рода. Поэтому — один primary, одна синхронная реплика, автоматическое промоутирование реплики при отказе primary (например, средствами оркестратора кластера PostgreSQL). RTO — минуты (время обнаружения отказа, промоушена реплики и переключения клиентов); RPO — близко к нулю за счёт синхронности реплики.

**Kafka: replication factor = 3, `min.insync.replicas` = 2.**
Каждая партиция каждого топика (включая `campaign.updated`, `campaign.budget.updated`, `campaign.activated`, `ad.impressions`, `ad.clicks`) хранится на 3 брокерах. `min.insync.replicas = 2` в паре с `acks=all` на продьюсере означает: запись подтверждается, только когда её получили минимум 2 из 3 реплик — потеря одного брокера не останавливает запись и не теряет данные, а потеря двух из трёх останавливает запись (сервис получит ошибку), а не молча продолжает писать в недостаточно реплицированном состоянии. Для событий, влияющих на списание средств (`ad.impressions`, `ad.clicks`) и на актуальность бюджета в Кеше (`campaign.budget.updated`), эта гарантия обязательна, а не опциональна.

**Redis: Cluster, не Sentinel.**
Sentinel добавляет автоматический failover к одному нешардированному Redis-инстансу, но не решает горизонтальное масштабирование — при росте числа кампаний и RPS до целевых 50 000 рабочий набор данных перестаёт помещаться и обслуживаться одним узлом. Redis Cluster даёт и то, и другое сразу: данные шардируются по хеш-слотам между узлами (масштабирование), и у каждого шарда есть реплика с автоматическим промоушеном при отказе первичного узла шарда (тот же failover, что даёт Sentinel, но на уровне каждого шарда, а не всего кластера целиком). Поэтому Cluster полностью покрывает то, что давал бы Sentinel, и добавляет масштабирование, которого Sentinel не даёт.

## Обратная совместимость при поэтапном выделении сервисов

Остальной документ описывает Сервис ставок в предположении, что Сервис кампаний уже существует как полноценный независимый сервис. На практике выделение происходит поэтапно, и какое-то время Сервис ставок будет работать против ещё не до конца выделенного Сервиса кампаний (например, часть данных о кампаниях временно остаётся в монолите). Совместимость на этот период обеспечивается так, чтобы код и контракт Сервиса ставок не зависели от того, где физически в данный момент живёт источник истины:

- **Контракт фиксируется на целевом состоянии заранее.** gRPC-интерфейс `CampaignService.GetActiveCampaigns` и схемы событий `campaign.*` (см. `interaction.md`) проектируются такими, какими они должны быть в целевой архитектуре, до того, как реальный Сервис кампаний физически выделен.
- **Фасад/адаптер поверх монолита.** Пока данные о кампаниях остаются в монолите, перед ним разворачивается тонкий адаптер, реализующий тот же gRPC-контракт и публикующий те же Kafka-события `campaign.*` — по факту изменений в монолите (например, через CDC на его БД или периодический diff). Сервис ставок обращается к этому адаптеру и ничем не отличает его от «настоящего» Сервиса кампаний.
- **Замена адаптера на реальный сервис — без изменений в Сервисе ставок.** Когда Сервис кампаний выделяется физически, адаптер заменяется им за тем же самым контрактом; Сервис ставок не требует ни изменения кода, ни повторного тестирования интеграции — для него ничего не поменялось.
- Это и есть практическое применение Strangler-подхода на границе именно этих двух сервисов: старый и новый контуры сосуществуют произвольно долго, разница между ними скрыта за одним и тем же контрактом.

**Идемпотентность:** финансовые операции по событиям показов/кликов выполняются Финансовым сервисом, а не Сервисом ставок — описание идемпотентности при потреблении событий из Kafka см. в [`interaction.md`](./interaction.md).
