# Взаимодействие между сервисами: протоколы и паттерны

## Выбор протокола по типу взаимодействия

| Взаимодействие | Протокол | Обоснование |
|---|---|---|
| DSP-партнёр → API Gateway → Сервис ставок | HTTPS / OpenRTB (JSON) | Внешний контракт задан индустриальным стандартом и партнёром; менять его AdScale не может |
| API Gateway → Сервис ставок (внутренний вызов) | gRPC | Критичный по SLA путь (бюджет 80 мс на весь запрос). gRPC даёт бинарную сериализацию (Protobuf) вместо JSON, HTTP/2 с мультиплексированием, встроенные таймауты и дедлайны на уровне протокола, строгую типизацию контракта. При десятках тысяч RPS экономия на (де)сериализации и накладных расходах транспорта — не микрооптимизация, а часть SLA-бюджета |
| Сервис ставок → Хранилище кампаний / Кеш | gRPC (к БД — стандартные драйверы, не gRPC) | Кеш — прямой клиент Redis (протокол Redis, не HTTP/gRPC); обращение к Хранилищу кампаний идёт не в hot path, а асинхронной фоновой синхронизацией |
| Рекламный кабинет (BFF) → Финансовый сервис / Сервис аналитики | REST/JSON | Не в критичном по времени отклика пути — рекламодатель просматривает отчётность и баланс, задержка в сотни миллисекунд не создаёт бизнес-риска. REST/JSON проще в отладке, кешировании на уровне HTTP и интеграции с браузерным клиентом Рекламного кабинета, не требует генерации клиентского кода как gRPC |
| Сервис выдачи → Сервис статистики → Очередь событий → (Сервис аналитики, Финансовый сервис) | Kafka (асинхронно) | События показов/кликов должны быть буферизованы и доставлены нескольким независимым потребителям (аналитика и биллинг читают один и тот же поток, не блокируя друг друга и не блокируя путь показа рекламы). Из альтернатив (RabbitMQ, managed cloud-очередь, Redis Streams) Kafka выбрана за счёт сочетания трёх свойств: высокая пропускная способность на уровне целевой нагрузки, независимые consumer-группы «из коробки» и настраиваемый срок хранения для повторного чтения истории при восстановлении потребителя или изменении логики агрегации |

**Итог по правилу выбора:** критичный по SLA синхронный путь → gRPC; некритичные по времени отклика синхронные обращения (в основном UI/отчётность) → REST; любая доставка событий с несколькими независимыми потребителями и требованием буферизации → Kafka.

## Нужен ли API Gateway

**Да.** Без выделенного шлюза каждый DSP-партнёр интегрировался бы напрямую с внутренним сервисом, что означает:
- Аутентификацию и rate limiting пришлось бы реализовывать внутри самого Сервиса ставок, смешивая бизнес-логику аукциона с сетевой/security-логикой.
- Смену внутренней декомпозиции (например, дальнейшее разделение Сервиса ставок на более мелкие сервисы) невозможно было бы делать без пересогласования контракта с каждым DSP-партнёром.
- Circuit Breaker и мониторинг латентности нужно было бы дублировать в каждом внутреннем сервисе, к которому обращается внешний клиент.

Какой именно шлюз и как он настроен для DSP — см. [`api-gateway.md`](./api-gateway.md).

## Дизайн событийных потоков (Kafka)

| Topic | Producer | Consumers (независимые группы) | Партиционирование |
|---|---|---|---|
| `ad.impressions` | Сервис статистики | Сервис аналитики, Финансовый сервис, Хранилище событий (writer) | По `campaign_id` — гарантирует порядок событий одной кампании внутри партиции, что важно для корректного порядка списаний |
| `ad.clicks` | Сервис статистики | Сервис аналитики, Финансовый сервис, Хранилище событий (writer) | По `campaign_id`, аналогично |

Срок хранения событий установлен с запасом на возможность повторного чтения истории при добавлении нового потребителя или пересчёте агрегатов Сервисом аналитики.

## Идемпотентность финансовых операций

Kafka гарантирует доставку at-least-once — сообщение может быть обработано потребителем более одного раза (например, при перезапуске Финансового сервиса после обработки, но до коммита offset). Поскольку событие показа/клика напрямую приводит к списанию средств, повторная обработка без защиты привела бы к двойному списанию.

**Механизм идемпотентности в Финансовом сервисе:**
- Каждое событие в топиках `ad.impressions` / `ad.clicks` несёт уникальный `event_id` (генерируется Сервисом статистики при публикации).
- Финансовый сервис перед списанием проверяет `event_id` в таблице обработанных событий (уникальный индекс) в рамках той же транзакции, что и само списание — запись `event_id` и обновление баланса происходят атомарно.
- При повторном поступлении события с уже известным `event_id` списание не выполняется повторно — операция становится идемпотентной по ключу события, а не по времени получения.

Это же событие (`event_id`) используется как идемпотентный ключ и при ретраях доставки со стороны Kafka producer (Сервис статистики) — при повторной публикации после сетевого сбоя без подтверждения от брокера `event_id` остаётся тем же, и потребитель корректно распознает дубликат.
