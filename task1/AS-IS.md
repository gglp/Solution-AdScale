# AS-IS: анализ текущей архитектуры AdScale

## Обзор текущей ИТ-инфраструктуры

AdScale — гибридный монолит (C++ / Go / Python / Node), развёрнутый на одном production-кластере, с единственной инстанцией PostgreSQL, без кеша, без очередей, без контейнеризации; деплой выполняется вручную. Архитектура не задокументирована. Внутри монолита работают:

- **Рекламный сервер** — принимает HTTP-запросы, определяет пользователей, подбирает кандидатов и передаёт их в Сервер аукциона; также напрямую читает данные для таргетинга из PostgreSQL; критичен по времени отклика.
- **Сервер аукциона** — применяет бизнес-правила взвешивания ставок и определяет победителя; наиболее чувствителен к задержкам; использует синхронные вызовы к базе данных.
- **Сервис выдачи** — формирует HTML/JS-разметку баннера и готовит response.
- **Сервис статистики** — пишет клики и показы напрямую в PostgreSQL без буферизации, создавая высокую write-нагрузку, конкурирующую с транзакционными запросами.
- **Финансовый сервис** — списание средств, выставление счетов, сведение балансов; работает в той же базе данных.
- **Сервис аналитики** — выполняет тяжёлые SQL-запросы напрямую в продакшн-базу; read-replica отсутствует, что приводит к блокировкам и росту времени отклика.
- **Рекламный кабинет** — UI для рекламодателей; backend встроен в монолит и использует ту же базу данных.

Помимо компонентов монолита, в текущем ландшафте есть две внешние системы: DSP-партнёр, обменивающийся с Рекламным сервером bid-запросами и ответами по протоколу OpenRTB, и Платёжный шлюз, через который Рекламный кабинет обрабатывает пополнение бюджетов рекламодателей; оба интерфейса сохраняются без изменений в рамках данного проекта.

Актуальное as-is состояние зафиксировано в C4-диаграмме контейнеров [`Diagrams/AS-IS.puml`](./Diagrams/AS-IS.puml).

## Узкие места и точки отказа

- PostgreSQL является единой точкой отказа и точкой конкуренции за ресурсы: она одновременно обслуживает транзакционную нагрузку аукциона, запись событий, финансовые операции и тяжёлую аналитику, а также напрямую используется 6 из 7 компонентов монолита — Сервер аукциона (синхронное чтение ставок/кампаний), Сервис статистики (прямая запись), Финансовый сервис (транзакции/балансы), Сервис аналитики (тяжёлые запросы), Рекламный кабинет (CRUD) и Рекламный сервер (чтение данных для таргетинга).
- PostgreSQL развёрнута в единственном экземпляре без резервирования (HA) и без read-replica — отказ базы одновременно останавливает работу всех зависимых компонентов монолита.
- Пики нагрузки поступают напрямую в базу данных, а запись событий выполняется без буферизации, что усиливает конкуренцию за её ресурсы.
- Компоненты монолита нельзя масштабировать независимо друг от друга, а деплой выполняется вручную, что повышает риск ошибок при выкладке.
- В штате нет выделенных SRE-инженера, технического писателя и бизнес-аналитика — некому в моменте вести надёжность системы и документировать архитектуру параллельно с разработкой.

## Влияние на время отклика

Уже сегодня, без дополнительной нагрузки от DSP-партнёра, система работает на пике 15 000 RPS с P95 110–120 мс (при требовании ≤ 100 мс) и периодически деградирует в часы пик — запас по производительности отсутствует. Ключевая причина — Сервер аукциона, самый чувствительный к задержкам компонент, зависит от синхронных вызовов к перегруженной базе: каждое решение аукциона требует обращения к PostgreSQL, конкурирующей за ресурсы с записью статистики, финансовыми транзакциями и тяжёлой аналитикой.

## Архитектурные проблемы, препятствующие масштабированию

1. **Отсутствие независимого масштабирования** — все компоненты монолита разворачиваются и масштабируются как единое целое; нельзя выделить ресурсы отдельно для самого нагруженного (Сервера аукциона) без масштабирования всей системы.
2. **Отсутствие изоляции критичных и некритичных потоков** — bid-запрос (критичный по SLA путь) и запись статистики/аналитика (некритичные по времени отклика) конкурируют за одну и ту же базу данных.
3. **Отсутствие кеширования** — каждое обращение к горячим данным (ставки, кампании) идёт в БД, а не в промежуточный слой.
4. **Отсутствие асинхронности** — запись событий (клики/показы) блокирующая и синхронная, вместо буферизованной через очередь.
5. **Ручной деплой и отсутствие контейнеризации** — увеличивает риск ошибок и не позволяет автоматически масштабировать отдельные компоненты под нагрузку.
