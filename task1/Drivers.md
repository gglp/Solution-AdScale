# Архитектурные драйверы

## Бизнес-контекст

Подключение нового крупного DSP-партнёра увеличивает трафик на 20% (с ~15 000 до ~18 000 RPS) немедленно, с прогнозом двукратного роста в течение года. Новый партнёр предъявляет более жёсткие требования: P95 времени отклика ≤ 80 мс, доступность (SLA) не ниже 99,9%, штрафы за простои. При этом систему нельзя переписать полностью — используется постепенная миграция при ограниченном бюджете, сроке 3 месяца на промежуточное решение и необходимости сохранить непрерывность обслуживания текущих рекламодателей.

## Функциональные требования к системе после интеграции

1. Система должна принимать и обрабатывать bid-запросы от текущего и нового DSP-партнёра по протоколу OpenRTB без изменения формата интеграции (HTTPS/OpenRTB сохраняется на всех этапах перестройки Рекламного сервера и Сервера аукциона).
2. Система должна определять победителя аукциона и возвращать bid response в рамках установленного времени отклика (SLA), не деградируя при росте количества одновременных bid-запросов.
3. Система должна продолжать обслуживать текущих рекламодателей — показ рекламы, работу Рекламного кабинета и пополнение бюджета через Платёжный шлюз — без перерывов на всём протяжении миграции.
4. Система должна фиксировать события показов и кликов для последующей статистики и аналитики, не создавая нагрузку на путь обработки bid-запроса.
5. Система должна корректно проводить финансовые операции (списание средств, выставление счетов, сведение балансов) без потери данных и независимо от нагрузки на остальные компоненты.
6. Система должна предоставлять рекламодателям отчётные и статистические данные (аналитика, история кампаний) без влияния на производительность критичного по времени отклика контура аукциона.
7. (Целевое состояние, горизонт — год) Система должна поддерживать независимое масштабирование сервиса ставок отдельно от остальных сервисов и горизонтальное развёртывание в нескольких регионах.

## Атрибуты качества (с приоритизацией)

| Требование | Описание | Приоритет |
|---|---|---|
| Производительность | P95 времени отклика ≤ 80 мс; на промежуточном этапе допустимый минимум — ≤ 100 мс | Высокий |
| Пропускная способность | Поддержка до 50 000 RPS на целевом этапе, не менее 18 000 RPS на промежуточном — без сбоев и таймаутов сервиса ставок | Высокий |
| Масштабируемость | Возможность независимо масштабировать наиболее нагруженные компоненты (Рекламный сервер, Сервер аукциона) без масштабирования всей системы целиком | Высокий |
| Доступность (SLA) | Отсутствие простоев, штрафуемых DSP-партнёром; целевой показатель SLA 99,9% на финальном этапе | Высокий |
| Разделение потоков | Изоляция критичных по времени отклика потоков (аукцион) от некритичных (статистика, аналитика, финансы) | Высокий |
| Безопасность | Защита финансовых данных и данных ставок, контроль доступа между сервисами при декомпозиции монолита | Средний |
| Сопровождаемость | Документирование архитектуры по мере декомпозиции — с учётом отсутствия штатного технического писателя | Средний |

## Ограничения

**Бизнес-ограничения:**

- Бюджет ограничен; срок 3 месяца на промежуточное решение — не позволяют провести полную переработку системы.
- Необходима непрерывность бизнеса: изменения выкатываются без остановки обслуживания текущих рекламодателей.
- В штате 35 человек нет выделенных SRE, технического писателя и бизнес-аналитика — доработки и их документирование ложатся на существующую команду, что ограничивает объём одновременно выполняемых изменений.

**Технические ограничения:**

- Изменения на промежуточном этапе ограничены существующим стеком (C++ / Go / Python / Node, PostgreSQL) с точечными добавлениями (кеш, очередь, read-replica), без смены базовых технологий.
- Формат интеграции с DSP-партнёром (bid-запросы и ответы по протоколу OpenRTB, HTTPS) должен быть сохранён без изменений при любой перестройке Рекламного сервера и Сервера аукциона.
