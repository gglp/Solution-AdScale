# ADR-003: Выбор технологии для потоковой обработки событий

**Дата:** 2026-09-12

**Статус:** Принято

## Контекст

Сегодня Сервис статистики пишет события кликов и показов напрямую в PostgreSQL без буферизации, создавая write-нагрузку, конкурирующую с транзакционными запросами. Целевая архитектура ([`TO-BE.md`](../TO-BE.md)) отделяет запись событий от транзакционного пути через асинхронную Очередь событий: Сервис статистики публикует события, а Сервис аналитики потребляет их для построения отчётности, не создавая нагрузку на боевую БД.

Ключевые архитектурные драйверы:
- Пропускная способность: до 50 000 RPS событий показов/кликов на целевом этапе
- Несколько независимых потребителей одного и того же потока: Сервис статистики и Сервис аналитики должны читать одни и те же события, не блокируя друг друга
- Возможность повторного чтения истории (replay) — для восстановления после сбоя Сервиса аналитики или добавления нового потребителя в будущем
- Совместимость с существующим стеком и посильная эксплуатационная сложность для команды без выделенных SRE

Рассматривались четыре альтернативы:
1. RabbitMQ
2. Managed cloud-очередь (например, Kinesis)
3. Redis Streams
4. Apache Kafka

### Альтернатива 1: RabbitMQ
Плюсы: проще в освоении, хорошо подходит для классических очередей задач.
Минусы: хуже приспособлен для высокопроизводительного event streaming с несколькими независимыми consumer-группами и длительным retention; replay истории событий не является его сильной стороной.

### Альтернатива 2: Managed cloud-очередь (например, Kinesis)
Плюсы: минимум эксплуатационной нагрузки на команду без SRE.
Минусы: вносит зависимость от конкретного облачного провайдера, чего проект сегодня не использует (собственный production-кластер); решение о переходе в облако не входит в рамки текущего проекта.

### Альтернатива 3: Redis Streams
Плюсы: уже используется в целевой архитектуре как Кеш — не требует нового компонента инфраструктуры.
Минусы: меньшая зрелость для аналитических нагрузок с длительным хранением и повторным чтением; риск конкуренции за ресурсы с Кешем для Сервиса ставок, если развернуть в том же кластере.

### Альтернатива 4: Apache Kafka
Плюсы: высокая пропускная способность, множественные независимые consumer-группы «из коробки», настраиваемый retention для replay, зрелая экосистема для интеграции с аналитическими хранилищами.
Минусы: требует отдельного кластера и эксплуатационных навыков; наиболее сложный в развёртывании вариант из рассмотренных.

## Решение

Выбран **Apache Kafka** в качестве Очереди событий (альтернатива 4). Целевая нагрузка (до 50 000 RPS) и необходимость нескольких независимых потребителей — это ровно тот сценарий, для которого Kafka спроектирована, в отличие от классических брокеров задач. Настраиваемый retention позволяет Сервису аналитики переобрабатывать историю событий при изменении логики агрегации без повторного обращения к прод-базе. Решение не вносит зависимость от облачного провайдера, что соответствует ограничению — изменения на промежуточном этапе ограничены существующим стеком без смены базовой инфраструктуры.

## Последствия

**Положительные:**
- Сервис статистики и Сервис аналитики полностью развязаны друг от друга и от транзакционного пути аукциона.
- Добавление нового потребителя событий в будущем (например, ML-модели для оптимизации ставок) не потребует изменений в Сервисе статистики.

**Отрицательные:**
- Эксплуатация Kafka-кластера — новая компетенция для команды без выделенного SRE; потребуется либо обучение, либо рассмотрение managed-варианта Kafka на более позднем этапе.
- Добавляет ещё один инфраструктурный компонент, который нужно мониторить и обслуживать.

**Риски:**
- Риск не уложиться в трёхмесячный срок из-за отсутствия выделенных SRE — эксплуатация нового Kafka-кластера ложится на действующую команду.
- Риск недостаточной эксплуатационной зрелости команды при первом запуске кластера в продакшн — потребуется дополнительное время на обучение или найм.
