# ADR-002: Выделение сервиса ставок в качестве первого приоритета

**Дата:** 2026-09-12

**Статус:** Принято

## Контекст

В рамках стратегии Strangler Fig ([ADR-001](./ADR-001-evolution-strategy.md)) части монолита выносятся поэтапно. Необходимо определить, какой компонент выносится первым, учитывая ограниченные время (3 месяца) и ресурсы команды.

Ключевые архитектурные драйверы:
- На AS-IS диаграмме Сервер аукциона отмечен как `<<Critical Path>>`, Рекламный сервер — как `<<Bottleneck>>`
- Требование нового DSP-партнёра: P95 ≤ 80 мс, штрафы за простои — привязано именно к этому пути
- Сервер аукциона использует синхронные вызовы к перегруженной БД в hot path — корневая причина сегодняшней деградации (P95 110–120 мс при требовании ≤ 100 мс)
- Срок 3 месяца не позволяет выносить несколько компонентов одновременно

Кандидатами на выделение выступают любые из семи компонентов монолита: Рекламный сервер, Сервер аукциона, Сервис выдачи, Сервис статистики, Финансовый сервис, Сервис аналитики, Рекламный кабинет.

Рассматривались три альтернативы:
1. Вынести Сервис статистики первым
2. Вынести Сервис аналитики первым
3. Вынести Bidding-контур (Рекламный сервер + Сервер аукциона) первым

### Альтернатива 1: Вынести Сервис статистики первым
Плюсы: убирает write-нагрузку без буферизации из общей БД, относительно простое изменение.
Минусы: не устраняет синхронную зависимость Сервера аукциона от БД — основной риск нарушения SLA с DSP-партнёром остаётся нетронутым.

### Альтернатива 2: Вынести Сервис аналитики первым
Плюсы: снимает тяжёлые аналитические запросы с prod-базы, снижает фоновую нагрузку на БД.
Минусы: аналогично — не решает проблему на критичном по времени отклика пути, где формируется основной бизнес-риск.

### Альтернатива 3: Вынести Bidding-контур (Рекламный сервер + Сервер аукциона) первым
Плюсы: напрямую устраняет корневую причину деградации P95 и адресует главное требование нового DSP-партнёра.
Минусы: требует объединения двух ранее раздельных компонентов монолита в один сервис и согласования границ их ответственности.

## Решение

Первым выносится **Сервис ставок** — объединение Рекламного сервера и Сервера аукциона в единый сервис с выделенным кешем (альтернатива 3). Остальные компоненты (Сервис статистики, Сервис аналитики, Финансовый сервис, Рекламный кабинет) выносятся на последующих этапах декомпозиции.

## Последствия

**Положительные:**
- Максимальное снижение риска для главной бизнес-цели проекта (удержание нового DSP-партнёра) в кратчайший срок.
- Кеш, введённый для Сервиса ставок, сразу снимает основную причину сегодняшних деградаций.

**Отрицательные:**
- Сервис статистики и аналитики продолжают работать с общей БД на промежуточном этапе.
- Объединение Рекламного сервера и Сервера аукциона в один сервис требует согласования границ ответственности между двумя ранее раздельными компонентами монолита.

**Риски:**
- Риск того, что даже после выделения Сервиса ставок единственная write-инстанция PostgreSQL останется узким местом при росте нагрузки до 18 000 RPS и выше (пока не вынесены Сервис статистики и Сервис аналитики).
- Риск нарушения консистентности данных при переводе Сервиса ставок с синхронных вызовов к БД на работу через кеш.
