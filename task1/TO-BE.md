# TO-BE: целевая архитектура AdScale

## Выбор архитектурного стиля

Рассматривались три варианта эволюции архитектуры.

| Вариант | Почему рассмотрен | Почему отклонён / принят |
|---|---|---|
| **Оставить монолит, оптимизировать по месту** (вертикальное масштабирование, тюнинг БД, точечные индексы) | Минимальные усилия и риск, ничего не переписывается | **Отклонён.** Не решает корневую проблему — все компоненты монолита обязаны масштабироваться вместе, а PostgreSQL остаётся единой точкой отказа и конкуренции за ресурсы. Не позволяет достичь ни P95 ≤ 80 мс, ни независимого масштабирования сервиса ставок, ни целевых 50 000 RPS. Работает только как временная мера. |
| **Полная переписка на микросервисы сразу** | Даёт «чистую» целевую архитектуру без промежуточных компромиссов | **Отклонён.** Несовместим с ограничениями: 3 месяца на первый результат, ограниченный бюджет, отсутствие выделенных SRE и бизнес-аналитика, требование непрерывности обслуживания текущих рекламодателей. Риск отказа системы, обслуживающей боевой трафик, неприемлем. |
| **Strangler Fig (постепенное выделение сервисов)** | Позволяет выпустить промежуточное решение за 3 месяца, не останавливая систему, и двигаться к целевой архитектуре поэтапно | **Принят.** Монолит продолжает работать и обслуживать нерефакторенные потоки, а наиболее критичные по SLA и нагрузке компоненты выносятся первыми (см. [`adr/ADR-001-evolution-strategy.md`](./adr/ADR-001-evolution-strategy.md) и [`adr/ADR-002-bidding-service-first.md`](./adr/ADR-002-bidding-service-first.md)). |

Модульный монолит (внутренняя модуляризация без физического выделения сервисов) специально не выбран как самостоятельный целевой стиль: он снял бы часть проблем со связностью кода, но не решает главное архитектурное ограничение — невозможность масштабировать Сервер аукциона независимо от остальной системы, а также не даёт изоляции БД для критичного по SLA пути. Тем не менее его отдельные практики (чёткие границы ответственности компонентов, минимизация связей через БД) применяются внутри монолита как подготовительный шаг перед выделением сервисов в рамках strangler-подхода.

## Целевая декомпозиция (горизонт — год)

| Сервис | Зона ответственности | База данных | Обоснование границы |
|---|---|---|---|
| **API Gateway** | Единая точка входа для всего внешнего трафика — bid-запросов от DSP-партнёров, запросов рекламодателей и конечных пользователей; маршрутизация, аутентификация, rate limiting | — (без состояния) | Изолирует внешние контракты (OpenRTB/HTTPS, UI/API) от внутренней декомпозиции: все внешние клиенты продолжают работать с одним стабильным интерфейсом, даже когда внутренняя архитектура меняется |
| **Сервис ставок** (объединяет Рекламный сервер + Сервер аукциона) | Приём bid-запроса, подбор кандидатов, взвешивание ставок, определение победителя — с P95 ≤ 80 мс | Собственная БД конфигурации кампаний/ставок (Хранилище кампаний) + Кеш (Redis) для горячего чтения | Самый нагруженный и чувствительный к задержкам путь всей системы (см. AS-IS: `<<Critical Path>>`, `<<Bottleneck>>`); выделяется первым и получает выделенные, приоритетные по ресурсам, независимо масштабируемые инстансы |
| **Сервис выдачи** | Формирование HTML/JS-разметки баннера и HTTP response | Без собственной БД (stateless); может кешировать шаблоны | Не хранит бизнес-данные, не имеет смысла выделять под него БД — только вычислительная логика |
| **Сервис статистики** | Приём и буферизованная запись событий кликов/показов | Собственное хранилище событий | Изолирует высокую write-нагрузку от транзакционного пути аукциона; пишет асинхронно через Очередь событий |
| **Сервис аналитики** | Тяжёлые аналитические запросы и отчётность для рекламодателей | Собственное аналитическое хранилище (DWH), заполняется потоком событий из Очереди событий | Убирает конкуренцию тяжёлых запросов за ресурсы с транзакционными БД остальных сервисов |
| **Финансовый сервис** | Списание средств за показы/клики (по данным из Очереди событий), выставление счетов, сведение балансов | Собственная транзакционная БД (изолированная) | Финансовые операции требуют строгой консистентности и изоляции от остальной нагрузки; не может делить БД с аналитикой или статистикой |
| **Рекламный кабинет (BFF)** | UI и API для рекламодателей — управление кампаниями, просмотр отчётности и баланса | Собственная лёгкая БД пользовательских настроек (при необходимости); данные кампаний, отчётности и баланса получает через API от Сервиса ставок, Сервиса аналитики и Финансового сервиса | Не дублирует данные других сервисов — работает как агрегирующий слой (Backend for Frontend) |

**Инфраструктурные компоненты:**

- **API Gateway** — единая точка входа для всего внешнего трафика: DSP-партнёры, рекламодатели, конечные пользователи.
- **Кеш (Redis, in-memory)** — горячие данные для Сервиса ставок; не хранит финансовые и аналитические данные.
- **Очередь событий (Kafka)** — событийная шина между Сервисом статистики и Сервисом аналитики (выбор технологии обоснован в [`adr/ADR-003-streaming-technology.md`](./adr/ADR-003-streaming-technology.md)).

## Взаимодействие между сервисами

- DSP-партнёр → API Gateway → Сервис ставок: синхронный вызов внутри критичного по времени отклика контура (OpenRTB/HTTPS).
- Пользователь сайта/приложения → API Gateway → Сервис выдачи: маршрутизация запроса на показ рекламы.
- Рекламодатель → API Gateway → Рекламный кабинет: маршрутизация запросов управления кампаниями.
- Сервис ставок → Кеш: чтение данных, необходимых для взвешивания ставок, без обращения к БД на каждый запрос.
- Сервис ставок → Сервис выдачи: передача победителя аукциона для формирования баннера.
- Сервис выдачи → Сервис статистики → Очередь событий → Хранилище событий: асинхронная, буферизованная запись событий показов/кликов.
- Очередь событий → Сервис аналитики → DWH: потоковая обработка событий для отчётности, без нагрузки на транзакционные БД.
- Очередь событий → Финансовый сервис: события показов/кликов как основание для списания средств (CPM/CPC).
- Рекламный кабинет → Финансовый сервис: операции с балансом и счетами.
- Рекламный кабинет → Сервис аналитики: чтение отчётных и статистических данных.
- Рекламный кабинет → Платёжный шлюз: пополнение бюджета (внешний интерфейс сохраняется без изменений).

## Путь от AS-IS к TO-BE

Переход выполняется поэтапно (Strangler Fig), без остановки обслуживания:

1. **Промежуточный этап (3 месяца).** Поверх существующего монолита точечно вводятся Кеш для Сервера аукциона, очередь для Сервиса статистики и read-replica для Сервиса аналитики; критичные и некритичные потоки разделяются по ресурсам, но общая БД пока сохраняется.
2. **Стабилизация / пилот (1–3 месяца).** Донастройка кеша и очередей под реальной нагрузкой от нового DSP-партнёра.
3. **Целевое решение (до 12 месяцев).** Полная декомпозиция на сервисы из таблицы выше, каждый — со своей БД; переход на событийно-ориентированную обработку, горизонтальное автомасштабирование, мультирегиональное развёртывание.
