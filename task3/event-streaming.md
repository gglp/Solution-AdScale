# Потоковая обработка данных

## Топики Kafka

| Topic | Producer | Consumers (независимые группы) | Ключ партиционирования | Тип |
|---|---|---|---|---|
| `ad.impressions` | Сервис статистики | Сервис аналитики, Сервис финансов, Сервис статистики (writer в Cassandra) | `campaign_id` | Обычный (retention по времени) |
| `ad.clicks` | Сервис статистики | Сервис аналитики, Сервис финансов, Сервис статистики (writer в Cassandra) | `campaign_id` | Обычный (retention по времени) |
| `campaign.updated` | Сервис кампаний | Cache-updater Сервиса ставок | `campaign_id` | Compacted (log compaction) |
| `campaign.budget.updated` | Сервис кампаний | Cache-updater Сервиса ставок, Сервис финансов (сверка) | `campaign_id` | Compacted (log compaction) |
| `campaign.activated` | Сервис кампаний | Cache-updater Сервиса ставок (прогрев кэша) | `campaign_id` | Обычный (retention по времени) |

Партиционирование по `campaign_id` для всех топиков гарантирует порядок событий одной кампании внутри партиции — важно и для корректного порядка списаний в Сервисе финансов, и для корректного применения обновлений конфигурации в кэше (позднее событие не должно применяться раньше более раннего).

**Compacted-топики** (`campaign.updated`, `campaign.budget.updated`) хранят только последнее значение по каждому `campaign_id`, а не полную историю изменений — это осознанный выбор: потребителю (cache-updater) для инвалидации/прогрева нужно только текущее состояние кампании, а не история его изменения, и compaction держит объём топика ограниченным независимо от частоты редактирования кампаний.

## Схема событий: Avro со Schema Registry

Формат — **Avro**, а не JSON, для всех перечисленных топиков, по трём причинам:

1. **Безопасная эволюция схемы.** Schema Registry проверяет обратную совместимость при регистрации новой версии схемы — производитель не может случайно сломать контракт с уже работающими потребителями (Сервис аналитики, Сервис финансов), которые могут обновляться независимо и не одновременно с производителем.
2. **Компактность.** Бинарная сериализация Avro существенно легче JSON при десятках тысяч событий в секунду — экономия на объёме передаваемых и хранимых данных ощутима именно на топиках `ad.impressions`/`ad.clicks`.
3. **Строгая типизация контракта.** Схема явно фиксирует поля и типы события — то же качество контракта, которое уже применяется для синхронного взаимодействия сервисов, распространяется и на асинхронное.

JSON как альтернатива не выбран: выигрыш в читаемости «на глаз» не окупает потерю безопасной эволюции схемы и накладные расходы на сериализацию при таком объёме событий.

## Группы потребителей (consumer groups)

Каждый потребитель из таблицы топиков — самостоятельная consumer-группа: она читает поток независимо от остальных, с собственным offset, и сбой или отставание одной группы не блокирует и не замедляет остальные. В частности:

- Сервис аналитики и Сервис финансов читают один и тот же поток `ad.impressions`/`ad.clicks`, не влияя друг на друга.
- Cache-updater Сервиса ставок — отдельная группа на `campaign.updated`/`campaign.budget.updated`/`campaign.activated`, полностью изолированная от событийного пути показов/кликов.

## Политика хранения

- `ad.impressions`, `ad.clicks` — срок хранения с запасом на возможность повторного чтения истории при восстановлении отставшего потребителя или пересчёте агрегатов Сервисом аналитики; конкретное значение — компромисс между стоимостью хранения и глубиной возможного replay, устанавливается операционно, а не архитектурным ограничением.
- `campaign.updated`, `campaign.budget.updated` — политика хранения не применяется в привычном смысле: это compacted-топики, Kafka сама вытесняет устаревшие значения по ключу, топик не растёт неограниченно независимо от времени.
- `campaign.activated` — умеренный срок хранения (событие используется только для прогрева кэша в момент активации, длительный replay не нужен).
