# Стратегия кэширования

## Что кэшируется

| Данные | Ключ | Назначение |
|---|---|---|
| Конфигурация кампании (ставка, статус, условия) | `campaign:{id}` | Основные данные для решения об участии в аукционе, без обращения к Сервису кампаний на каждый bid-запрос |
| Индекс кампаний по таргетингу | `targeting_index:{geo}:{device}` | Быстрый отбор кандидатов (Redis Set) без полного перебора и без запроса к БД на каждый bid-запрос |
| Остаток бюджета кампании | `budget_remaining:{campaign_id}` | Атомарная проверка и декремент (`DECRBY`) прямо в hot path — предотвращает перерасход бюджета без синхронного обращения к Сервису финансов |

Кампании, ставки и бюджеты кэшируются полностью — это единственные данные, к которым обращается Сервис ставок в критичном по времени отклика пути.

## Где размещён Redis

**Redis Cluster** (не единственный инстанс) — горизонтально масштабируется вместе с ростом RPS и переживает отказ отдельного узла без полной потери кэша (данные распределены по хеш-слотам с репликами). Кластер размещается в той же зоне доступности (AZ), что и инстансы Сервиса ставок, которые его используют, — сетевая задержка до кэша входит в бюджет 80 мс, и лишний межзональный переход эту задержку неоправданно увеличивает. При мультирегиональном развёртывании — отдельный Redis Cluster на регион, без синхронной репликации между регионами (кампания, активная в конкретном регионе, кэшируется локально для него).

## TTL и стратегия инвалидации

Комбинация активной инвалидации (основной механизм) и TTL (страховочный):

- **Активная инвалидация.** Сервис кампаний публикует события изменения (`campaign.updated`, `campaign.budget.updated`) при любом обновлении конфигурации или бюджета. Cache-updater Сервиса ставок потребляет эти события и немедленно перезаписывает соответствующие ключи в Redis — без ожидания истечения TTL. Это основной путь обновления: bid-запрос в hot path никогда не ждёт синхронного похода в Сервис кампаний при промахе кэша по бизнес-логике.
- **TTL как страховка.** На случай сбоя доставки события (потребитель отстал, инцидент в Kafka) на ключи `campaign:{id}` и `targeting_index:*` установлен TTL порядка нескольких минут — чтобы устаревшая конфигурация в худшем случае не жила в кэше неограниченно долго, а не как основной механизм обновления.
- **`budget_remaining` — особый случай.** Значение изменяется на каждой выигранной ставке (атомарный `DECRBY`), а не только при явном редактировании кампании, поэтому TTL для него короче и дополнена периодической сверкой с авторитетным балансом Сервиса финансов (коррекция возможного дрейфа значения без блокировки hot path).

## Прогрев кэша (cache warming)

- **При старте инстанса Сервиса ставок.** Новый инстанс не принимает трафик (readiness probe не готова), пока не загрузит в Redis данные по активным кампаниям из Сервиса кампаний — иначе первые bid-запросы после запуска или деплоя ловили бы холодный кэш прямо в hot path.
- **При активации новой кампании.** Событие `campaign.activated` не только обновляет запись в кэше, но и заранее прогревает `targeting_index`, чтобы первый же bid-запрос, подходящий под условия таргетинга новой кампании, увидел её как кандидата — без задержки на «первое обращение создаёт кэш».
- **Прогрев, а не ожидание промаха.** Общий принцип: кэш наполняется проактивно, по событиям от Сервиса кампаний, а не реактивно — по первому cache miss в hot path. Реактивный промах в этой архитектуре — признак сбоя (обрабатывается отдельным fallback-механизмом на уровне надёжности сервиса), а не штатный путь заполнения.
