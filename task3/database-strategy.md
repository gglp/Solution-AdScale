# Database per Service: выбор хранилища

Каждый сервис владеет собственной базой данных, недоступной напрямую другим сервисам (Database per Service) — доступ к чужим данным только через API или события. Выбор типа хранилища для каждого сервиса определяется профилем нагрузки и требованиями к консистентности, а не единым стандартом на всю систему.

## Сводная таблица

| Сервис | Тип базы данных | Обоснование |
|---|---|---|
| Сервис ставок | Redis (in-memory key-value), собственный read-реплицируемый слой | Сервис не хранит источник истины — только денормализованную, оптимизированную под чтение копию активных кампаний и остатков бюджета, обновляемую асинхронно из событий Сервиса кампаний. При бюджете P95 ≤ 80 мс любое обращение к дисковой БД в hot path недопустимо; in-memory key-value с O(1)-доступом по ключу кампании/таргетинга — единственный вариант, укладывающийся в этот бюджет |
| Сервис кампаний | PostgreSQL (реляционная) | Источник истины по конфигурации кампаний, таргетингу, бюджетам и креативам — данные с чёткими связями (кампания → таргетинг-правила → креативы) и требованием ACID-транзакций при обновлении бюджета (нельзя допустить гонку при одновременном редактировании). Объём данных невелик (тысячи кампаний, не события), реляционная модель и её гарантии здесь важнее горизонтальной масштабируемости |
| Сервис статистики | Apache Cassandra (wide-column) | Приём событий показов/кликов — экстremально высокая write-нагрузка (десятки тысяч событий в секунду на пике), линейно растущая вместе с RPS. Cassandra спроектирована именно под такой профиль: masterless-репликация, запись без единой точки блокировки, линейное горизонтальное масштабирование добавлением узлов. Строгая консистентность здесь не требуется — eventual consistency приемлема для лога событий |
| Сервис аналитики | ClickHouse (колоночная OLAP) | Тяжёлые агрегирующие запросы и отчётность для рекламодателей (суммы показов/кликов по кампании, дню, гео за произвольный период). Колоночное хранение и векторизованное исполнение на порядок быстрее строковых БД именно для таких запросов; горизонтальное шардирование и репликация — встроены в СУБД |
| Сервис финансов | PostgreSQL (реляционная), изолированный инстанс | Списание средств, выставление счетов, балансы — операции, где обязательны ACID-транзакции и строгая консистентность (деньги нельзя терять или задваивать). Объём операций на порядки ниже сырых событий показов/кликов (агрегируется), поэтому реляционная БД без специального масштабирования справляется с нагрузкой |

## Отказоустойчивость данных (RPO/RTO, резервное копирование)

| Сервис | RPO | RTO | Стратегия |
|---|---|---|---|
| Сервис кампаний | Близко к нулю (минуты) | Минуты (автоматический failover на реплику) | Синхронная репликация на резервный узел + непрерывное архивирование WAL; полный бэкап ежедневно, WAL — непрерывно, хранение 30 дней |
| Сервис финансов | Ноль (потеря финансовых данных недопустима) | Минуты (автоматический failover) | Синхронная мультизональная репликация, point-in-time recovery по WAL; полный бэкап ежедневно, WAL — непрерывно, хранение — расширенное (для аудита) |
| Сервис ставок (Redis) | Не применимо — данные производные и пересобираемые | Минуты (время прогрева кэша) | Резервное копирование не требуется: при потере узла кэш восстанавливается прогревом из Сервиса кампаний и потока событий (см. `caching.md`) |
| Сервис статистики (Cassandra) | В пределах срока хранения топиков Kafka (события можно переиграть) | Часы (для полного восстановления узла из снапшота) | Устойчивость к отказу узла — за счёт коэффициента репликации Cassandra (RF = 3, кворумная запись/чтение), а не резервного копирования; периодические снапшоты — для восстановления за пределами срока хранения Kafka |
| Сервис аналитики (ClickHouse) | В пределах срока хранения исходных событий (пересчёт из Хранилища событий) | Часы (может потребоваться переобработка данных) | Периодические бэкапы (`clickhouse-backup`); при потере данных возможен пересчёт агрегатов из Сервиса статистики / Kafka, если данные ещё не вышли за срок хранения |

## Соответствие принципам 12-факторных приложений

- **Backing services как подключаемые ресурсы.** Каждая БД (PostgreSQL, Redis, Cassandra, ClickHouse) и Kafka подключаются сервисом как внешний ресурс через конфигурацию (connection string), без предположений о её физическом расположении — замена инстанса не требует изменения кода.
- **Конфигурация через переменные окружения.** Учётные данные и адреса БД не хранятся в коде/образе — передаются через окружение, отдельно для каждого окружения (dev/staging/prod).
- **Сервисы без состояния (stateless processes).** Сами процессы Сервиса ставок, Сервиса кампаний и т.д. не хранят состояние между запросами — всё состояние вынесено в перечисленные backing services; это позволяет свободно масштабировать число инстансов каждого сервиса по горизонтали.
- **Быстрый запуск и корректное завершение (disposability).** Особенно важно для Сервиса ставок: инстанс не принимает трафик, пока не завершит прогрев локального кэша (см. `caching.md`), и корректно отдаёт соединения при остановке — это часть стратегии отказоустойчивости, а не только процесс деплоя.
- **Паритет dev/prod.** В dev/staging используются те же типы БД (PostgreSQL/Redis/Cassandra/ClickHouse), что и в проде — на меньшем объёме, но без замены на легковесные аналоги, чтобы не терять специфичное для СУБД поведение при отладке.
