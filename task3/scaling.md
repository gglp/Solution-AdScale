# Масштабирование баз данных

## Репликация Master-Slave

Применяется там, где источник истины — одна реляционная БД (PostgreSQL), а не изначально распределённая СУБД:

| Сервис | Репликация | Назначение |
|---|---|---|
| Сервис кампаний | Master-Slave (1 primary + ≥1 read-реплика) | Replica снимает нагрузку чтения (управление кампаниями через Рекламный кабинет) с primary и служит горячим резервом для failover |
| Сервис финансов | Master-Slave (1 primary + синхронная реплика) | Реплика здесь в первую очередь для отказоустойчивости (RPO = 0), не для масштабирования чтения — объём финансовых операций умеренный |

Сервис статистики (Cassandra) и Сервис аналитики (ClickHouse) используют собственные, не Master-Slave, модели репликации — см. ниже.

## Шардирование

| Сервис | Шардировать? | Ключ шардирования | Обоснование |
|---|---|---|---|
| Сервис статистики (Cassandra) | Да | `(campaign_id, date_bucket)` — составной partition key | Чистое `campaign_id` привело бы к неограниченно растущим партициям для долгоживущих кампаний с большим трафиком; добавление суточного бакета держит размер партиции предсказуемым и ускоряет типовые запросы «события кампании за день» |
| Сервис аналитики (ClickHouse) | Да | `PARTITION BY toDate(event_time)`, распределение по шардам кластера — хеш `campaign_id` | Партиционирование по дате даёт эффективное удаление/архивирование старых данных и ускоряет запросы с фильтром по периоду; шардирование по хешу `campaign_id` равномерно распределяет нагрузку кампаний по узлам кластера |
| Сервис кампаний (PostgreSQL) | Нет | — | Объём данных — тысячи кампаний, а не события; укладывается в один инстанс с read-репликами, шардирование добавило бы сложность без выигрыша |
| Сервис финансов (PostgreSQL) | Нет (на текущем масштабе) | — | Объём агрегированных финансовых операций на порядки ниже сырых событий; при значительном росте число рекламодателей — кандидат на будущее шардирование по `advertiser_id`, но не требуется сейчас |
| Сервис ставок (Redis) | Не в классическом смысле | — | Горизонтальное распределение достигается через Redis Cluster (хеш-слоты по ключу кампании/таргетинга), а не ручное шардирование — см. `caching.md` |

## Read replicas для Сервиса аналитики

Да, необходимы. Дашборды и отчётность рекламодателей — тяжёлые ad-hoc агрегирующие запросы, которые не должны конкурировать за ресурсы с непрерывной записью потока событий из Kafka. Read-реплики (дополнительные узлы кластера ClickHouse) отделяют путь чтения от пути записи: запись — на узлы, принимающие поток из Kafka, чтение отчётности — на реплики, синхронизируемые асинхронно.

## Применение CQRS

CQRS (разделение моделей записи и чтения) применяется на границе **Сервис кампаний ↔ Сервис ставок**:

- **Command-сторона (запись):** Сервис кампаний — единственный источник истины, владеет нормализованной реляционной моделью (кампании, таргетинг-правила, бюджеты), принимает изменения через Рекламный кабинет.
- **Query-сторона (чтение):** локальный Redis-слой Сервиса ставок — денормализованная модель, оптимизированная под единственный сценарий чтения (быстрый отбор кандидатов по таргетингу в hot path), заполняется асинхронно через события из Сервиса кампаний (см. `event-streaming.md`).

Аналогичный паттерн — между **Сервисом статистики и Сервисом аналитики**: сырые события (command-сторона, append-only) публикуются в Kafka, а Сервис аналитики строит из них отдельную, оптимизированную под агрегирующие запросы read-модель (денормализованные агрегаты в ClickHouse), не читая напрямую из Cassandra Сервиса статистики.

**Где CQRS не применяется:** Сервис финансов — единая модель для записи и чтения балансов и счетов. Разделение моделей здесь не оправдано: объём операций умеренный, а расхождение между write- и read-моделью для финансовых данных создаёт риск консистентности, который в этом сервисе недопустим.
